### 一、业务职责与范围

- **不良管理只负责申报和入仓。** 保存工单、Execution、实际工序、数量、原因、工废/料废分类、操作者、时间及正式入库关联；区分待入仓、部分入仓、已入仓，防止重复入库。入仓后仓库之间流转、出库和最终处置归仓储，不回写为不良模块的物流流程。
- **取消专门返工能力。** 不再提供返回发现/申报节点、任选上游、返工分配/开始/结果、返工恢复产量或仓内领出返工的新命令。系统不编排技术部门评估及重新加工。当前仍在源码中的返工写入口、前端及相关测试需随实施退役，不能只隐藏按钮。历史已发生的返回/调整及处理事实仍须可读，继续按原有含义参与数量计算，不删除、重写或自动转换。
- 已有不良品/报废品正式入库复用统一库存能力；不良不自动等于报废，入报废品仓也不自动等于最终核销。分类、入库类型、目标仓用途及来源权限仍按现有有效规则审查，不把“简化”理解为任意仓库/类型均可绕过校验。
- **通用调拨单另立任务核查/设计，不纳入本次收尾改造。** 报废最终处置出库、已全部入库关闭后才发现质量问题的完整业务、BOM/多材料、ERP库存命令均后置。

### 二、术语与唯一数量口径

全部取当前正式有效事实、同一生产产出单位和统一ProductionQuantityService口径，不合并不同单位，不使用计划反推事实，不累加每道工序报工。

| 符号 | 定义 |
| --- | --- |
| I | 当前Execution正式确认投入，按产出单位；未决投产/领料另作为门禁 |
| G | 末道当前有效净产出，沿用统一投影；它不是含不良的末道原始报工，也不是所有工序报工之和 |
| D | 当前Execution各实际节点有效净不良损失之和，独立/重叠、订正/作废及历史返回均按原有唯一算法去重；入仓数量不是新增损失 |
| R | 关联该Execution、已经审核生效且与正式库存动作一致的累计正常生产净入库数量；草稿不计，不良/报废入库不计入R |
| Q | 已申报有效不良对应的累计正式质量入库数量，与原申报/处置/Execution/单据明细/动作可追溯；只证明不良实物交接，不再加到G、D或正常入库中 |
| P | 工单计划数量，按相同产出单位 |

数量例：投入100、末道原始报工100、末道有效不良10，则G=90、D=10；正常入库R=90，不良入库Q=10。工单贡献是R+D=100，不能用原始报工100再加不良10，也不能再加Q变成110。

上游损失例：投入100，上道有效不良10、下道报工90且无新增不良，则G=90、D=10，贡献仍100。禁止只取末道不良或累加两道报工。这里的“净”是不可变事实及合法调整后的当前净额，不表示允许新增返工流程。

### 三、Execution完全入库条件

审核完成后，仅复查正式关联的Execution；新业务符合全部条件才进入具有“完全入库”语义的正式状态：

1. 保留原有实际锁定路径、正式投入、来源/当前模式、工单/产品/工艺引用、无未决投产/领料、无待核实/未完成不良处理、数量合法及幂等等门禁。
2. 原有生产数量守恒成立：**I = G + D**。
3. 正常品累计正式入库闭合：**R = G**。R<G只是部分入库，R>G是数量异常，均不能标记完全入库；不能因为有任意一笔入库就通过。
4. 有效不良均已完成正式入仓交接，不能仅靠人工改成“已处理”绕过。Q及逐申报剩余量按真实质量来源关系验证，避免仅总量相等但来自别的申报。

因此投入100但只报工10、入库10，虽然R=G，也因I≠G+D不能完全入库。全部不良时G=R=0不是自动满足所有条件：仍需I=D、全部有效不良正式入仓、无未决状态，由质量入库审核触发收尾；不得要求再造一张数量为0的正常生产入库单。

**问题与入口：** `/api/system/user/importData` 调用四参数 `importUser`，该实际重载没有事务；循环中的 `this.insertUser/updateUser` 绕过代理，可在账号或关联表已写入后因撤销 outbox 要求事务而报错。给未使用的旧重载加事务不能修复真实入口。

- **依赖：** 重叠写入入口清单、现有数据范围协议和角色并发策略；与 S1.2 可分别实施，不共用一个大事务。

#### S1.4 / QA-09：配置、字典缓存与数据库提交一致

**问题与入口：** `SysConfigServiceImpl`、`SysDictDataServiceImpl`、`SysDictTypeServiceImpl` 在提交前写无过期缓存，回滚后仍可能读到未提交值。配置改键、字典项换类型、字典类型改名还涉及旧键清理。

- **代码范围：** 上述三个 Service、`DictUtils`、相关 Redis 调用及加载/重置入口；优先复用 `CommitActions` / `SpringCommitActions`，保持系统模块依赖方向。只审查受影响的配置/字典缓存，不扩展重写会话、路由或全部业务缓存。
- **提交边界：** 写事务内不发布新缓存；提交后失效涉及的旧/新键，从已提交数据重建。检查“写事务内读取 miss 导致回填”旁路、批量操作和手动重载，禁止它们提前发布事务内值。
- **并发与故障：** 实施前冻结提交后 Redis 失败的恢复方式，以及并发旧值回填的处理协议和最大陈旧窗口；优先用现有提交回调、失效、有限 TTL 和明确重试形成小范围方案。不能只移动一次 `set` 就宣布一致，也不能在数据库已提交后伪称回滚。依赖安全配置的操作在缓存状态不可判定时须按已提交权威值处理或明确失败。具体 TTL/恢复时限须在实现验收前数值化，不改 Factory 路由缓存的既有决定。
- **依赖：** 各类键的生产者/消费者清单、提交回调语义与缓存故障响应契约。此处不预设新增数据库 outbox 或竞争性的缓存框架。
- **验收：** 回滚、rollback-only、提交故障均不留下未提交缓存；改键/改类型正确失效旧新键；批量中途失败无半发布；提交后 Redis 故障可识别且在约定时限恢复；写事务读 miss 不泄漏；并发迟到回填符合声明的陈旧上限；真实 MySQL 与 Redis 故障场景另留证据。

#### S1.5 / QA-01：物料基本单位与历史计量身份保护

**问题与入口：** 普通编辑及同步 `upsert` 可直接修改物料基本单位，现有余额和历史数量随当前主数据被重新解释；仅禁用页面选择器无法保护同步和并发写入。

- **代码范围：** `MaterialServiceImpl.updateById/upsert`、`BasicDataRules`、`UnitMeasureServiceImpl`、`StockReferenceRules`、物料/单位 Mapper 和关联引用校验；前端物料单位编辑提示按需适配。盘点库存余额、库存动作、仓储明细、工单用料、领退料、投产及其他冻结单位引用的实际创建/删除入口，不把示例清单当成全部引用。
- **业务边界：** 已有余额、历史事实或单位引用的物料不得直接换基本单位；余额为零、冲销、VOID 不等于从未有事实。相同单位的其他合法编辑及无引用物料换单位继续可用。单位删除覆盖所有实际直接引用，不只检查当前物料。历史取消/撤销按原冻结事实执行，不因新增保护失去合法恢复能力。
- **事务与并发：** 物料换单位、同步更新、单位删除和相关引用创建采用一致的事务/锁协议；先盘点现有物料/单位/库存锁，再确定全入口一致的锁顺序，避免反序死锁或检查后新增引用。复用生成 Mapper/Example 和现有业务规则，不新增单表 ExtraMapper 或业务表 `factory_id`。
- **数据边界：** 不重写历史数量、不自动换算、不回填来源。现有异常数据先只读列清单并标识人工核实；若确需结构变更，另做新增正式迁移和数据方案，不重写已发布迁移。当前方案不预设增加字段或执行修数。
- **依赖：** 完整引用与锁顺序清单、原单位/数量冻结方式核实、指定业务库及 Factory 绑定复核；可和 S1.1–S1.4 分开交付。QA-02 的通用引用并发治理后续展开，但本项单位身份所需的创建/删除竞争不能推迟。
- **验收：** 无引用可换、有余额/零余额历史/冲销事实均拒绝换；普通编辑与同步入口表现一致；直接历史单位引用阻止删除；“换单位与新建库存/用料”“删除单位与新建物料”双事务竞争只产生合法结果；原业务撤销通过；跨厂相同本地主键互不影响。先做隔离回归，再在核实的 SIMPLE_B 业务库做受控 API/UI 验收，不修改用户历史事实。
