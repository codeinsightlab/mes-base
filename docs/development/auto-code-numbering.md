# 自动单据编号

自动编号由中心库服务提供。业务侧公共入口为 `AutoCodeNumbering.getDocNo(type)`；`type` 必须是“自动编码规则”页面中配置的规则编码 `ruleCode`。服务从可信的当前线程 `FactoryContext` 读取工厂 ID，调用方只传规则编码。每次调用都会分配一个新号码，因此它不是请求幂等键。业务请求重试时，应先读取已经保存的业务结果。

## 规则配置

规则及其组成在“系统 → 自动编码规则”中维护。规则可以不指定工厂作为全局规则，也可以指定一个工厂作为专属规则；规则编码在全局范围保持唯一，是业务调用的 type 身份；创建后普通编辑不能改码，确需改码须先审查业务调用、字典配置和历史引用。每条规则还要选择固定字典中的单据类型：`WORK_ORDER`（工单）、`STOCK_OUT`（出库单）或 `STOCK_IN`（入库单）。新建工单仅提供工单规则，候选包含当前工厂专属规则与全局规则；后端再次校验规则类别及工厂范围。库存单据的类型字典 `dict_value` 与 `ruleCode` 使用同一个业务 key（例如 `MATERIAL_ISSUE`），服务按类型精确匹配规则，并校验 `IN → STOCK_IN`、`OUT → STOCK_OUT`，不另建业务类型映射表。若同类规则同时有全局和当前工厂规则，自动生成用例优先使用工厂专属规则。

页面新增时在一个表单填写规则编码、名称、单据类别、固定前缀及必要工厂范围。保存通过 `POST /api/system/autocode/rule` 一次提交 `{rule, prefix}`，服务在同一中心事务先保存规则，再自动初始化以下三段；任何子项失败整单回滚。默认最大长度为64、不补齐整号、启用。无需先保存主表再逐条新增组成。

编辑通过 `GET /api/system/autocode/rule/{id}/document` 读取规则、完整组成及配置版本，再以 `PUT /api/system/autocode/rule` 一次提交 `{rule, prefix, version}`。名称、说明、启停等允许字段可正常修改。标准三段规则的前缀可修改，保留原 rule_id、part_id、日期与流水设置及已有计数，不重写历史单号；新号码采用新前缀并接续当天流水。配置或组成已被其他操作修改时拒绝旧版本保存，用户重新加载后再编辑。已有高级组成仅编辑规则信息时提交 `prefix=null`，原组成保持原样，页面明确引导到高级组成维护；空组成规则可在表单明确填写前缀后补齐三段。规则和新组成的创建、更新操作者由服务端认证身份明确传入；补齐组成归本次操作者，原规则创建人和创建时间保留，客户端填写审计字段不生效。

规则编码仍是通用入口 `getDocNo(type)` 的 `type`。单据创建服务使用带类别校验的取号入口，但调用方无需提供工厂 ID。工单或库存单据的正式取号契约按顺序使用以下三段：

规则编码长度为 1 到 64 位，只允许 ASCII 字母、数字、下划线和连字符，首位可为字母或数字。例如 `5600-` 是合法编码；不接受空格、斜杠或其他标点。

1. `FIXCHAR`：固定前缀，例如 `SO` 或 `RK`。
2. `NOWDATE`：日期格式为 `yyyyMMdd`。
3. `SERIALNO`：起始值为 `1`、步长为 `1`、启用 `DAY` 日周期，段宽至少为 `3`。

此类规则不要启用整号补齐。配置不符合契约时，服务会明确报错，不会替换成默认规则、前缀或其他标识。升级时只有已有 `WORK_ORDER` 规则会被分类为工单规则；其他历史规则保持未分类，可由管理员明确分类，不会被静默解释。

服务接口 `previewDocNo(type)` 和 `getDocNo(type)` 使用同一套配置解析与格式化，并共同校验上述契约。预览不写入计数，正式取号才会推进流水。非目标规则及组成仍保留，但调用这两个接口时会因配置不符合契约而失败。“系统 → 自动编码规则”页面上的通用预览和生成工具属于平台配置检查，不会分配工厂业务单号。业务单号由配置前缀、服务端日期和规则每日流水组成，例如 `WO20261027001`。流水段的宽度是最小宽度：`999` 之后自然变为 `1000`、`1001`。最终号码仍须符合规则最大长度和数据库结果列的 64 字符上限。

## 流水与缓存

规则配置以完整、不可变快照缓存，并按规则编码索引。快照包含全部规则及组成，不从分页 HTTP 结果拼接；组成由批量查询读取。规则或组成变更只有在中心事务提交后才会使共享快照失效。Redis 版本令牌阻止失效前启动的旧加载在失效后覆盖新快照。Redis 不可用时，服务从中心库读取当前配置，不会把缓存故障当作旧配置仍然有效的证明。

计数按规则身份、工厂 ID 和周期键分别持久化。每日业务流水使用 `rule_id + factory_id + F:<factoryId>|DAY:yyyyMMdd`。`cycle_key` 中的工厂标记也避免升级期间旧版读取器仅按规则和周期查询时与新工厂流水冲突。空工厂 ID 保留给历史/平台工具；有效业务工厂 ID 不为空。中心数据库的规则行锁会串行化多实例取号，也保护首次创建计数行。进入事务后，服务会通过数据库锁定读重新读取规则和组成；因此缓存陈旧或 Redis 失效失败都不能让停用或已变更的配置继续授权取号。规则类别与组成在同一份全局快照中，增删改或启停规则及其组成会在提交后使整份快照失效。失效失败时，新配置可能要等缓存 TTL 到期后才对缓存命中可见；正式取号仍以锁定读校验当前规则。缓存规则对象不包含可变流水状态，计数更新也不会淘汰配置缓存。日期段、日周期和生成时间共用同一个 `Asia/Shanghai` 服务端时间值。

中心库取号与后续工厂业务保存是两个事务。业务保存失败时号码可能被占用但未使用；本服务不承诺跨库事务或业务请求幂等。工单新建时可选择适用规则；库存单据及扫码领料使用单据类型的同名业务 key 取号，不能通过其他同类别规则替代缺失的类型规则。不创建规则与单据的持久绑定。需要回显时只能按单号前缀匹配，不能据此前缀匹配结果宣称建立了持久关联。名称等不改变身份的基本信息编辑，以及标准三段表单的前缀编辑，不扫描所有工厂的历史单据；历史单号是已经持久化的事实，不随当前配置改写。规则删除及适用工厂变更仍先在中心事务外检查原范围引用，再在短中心事务锁定复验；存在生成计数时禁止删除或变更工厂。全局规则删除扫描所有已启用且绑定可用业务库的工厂，专属规则只扫描指定工厂，不能核对时明确拒绝；中心库绑定不作为业务引用扫描目标。高级组成页保留原有的前缀引用与已取号保护，避免通过单段维护改变已用高级规则的编号依据。没有前缀的分类规则不能正式取号；未分类且无固定前缀的规则不能安全判定引用时拒绝删除。
