## 2. 四项决策的实现

1. **净报工转工序聚合加工量。** 原 `ProductionReport` 每条仍保存旧净报工、实际操作人、原报工时间；不把累计损耗加给任一员工。按 Execution + 实际节点 + 主投入物料/单位证明累计损耗，受控历史节点证据保存原净量、加工量修正、有效损耗及原质量行。正式 `ProductionQuantityService` 读取该证据，以原净报工合计加修正得总加工量，再扣历史有效损耗。历史分支与正常 LOCAL 分支明确区分，数量权威仍只有一套。
2. **历史投入。** 继续用流程卡、`pro_material`、材料镜像、`pro_buckle` 和 `qtyPer` 证据恢复投入；不依赖旧 ERP 工单头。工单计划量取全部已证明流程卡投入，计划起止取整单最早/最后报工时间。没有领料、出库、`PRODUCTION_INPUT`、实际库存或正式投产补造，旧 `mo_id` 不进入目标工单业务字段。
3. **最小历史只读状态。** WorkOrder/Execution 增加 `HISTORICAL`，来源持久化 LOCAL。正式查询投影可识别历史；历史投入仅用于解释，`writable=false`、当前可报量 0。Service 状态锁拒绝正式写入口，数据库补充保护覆盖未重启的旧应用。没有第二套可写生产核心，也没有全局跳过校验开关。
4. **锻接依赖隔离。** 综合 route flag、所有 broken-step 行、旧工单/流程卡/route、锻接后物料批次到领料关系构图，隔离整个关联工单组件。仅保存私有清单及未解析关系，不执行锻接写入。

历史质量 17 行保存在明确可查的 `QUALITY_EVIDENCE` 和节点聚合中；没有强行生成正常质量核实/恢复/放行或 `mes_production_defect`。正常质量流水因此不会伪装显示这些历史申报；历史接口承担原始证据查询。

## 3. 模型、Flyway 与执行入口

正式 V40 `legacy_production_history` 已执行：两张表 `mes_legacy_migration_batch`、`mes_legacy_source_mapping`。业务表不增加 factory_id。Mapping 只有 `entity_kind + entity_id` 一套权威目标引用，`parent_id` 表达从属；保存来源稳定身份、原文、内容哈希、转换证据、规则版本和批次。仅主键承担唯一约束，保留普通索引与中文注释，Mapping 禁止 UPDATE/DELETE。

批次状态为 PREPARED / REVIEWED / RUNNING / COMPLETED / FAILED / CONFLICT，冻结快照和完整 typed command 哈希绑定审批范围及操作人。内部 Service 无公共导入 HTTP、默认启动任务或调度器；通过现有 Factory/Owner 受管入口及 `businessTransactionManager` 执行。每个工单组件一个事务，状态、业务实体和来源 Mapping 原子提交。来源键由实例 UUID + schema + 来源类型 + 来源主键计算，不随规则或批次改变。

同批次通过数据库行锁串行；不同批次竞争相同来源最终受稳定 Mapping 主键约束保护，冲突方整组件回滚。当前真实并发证据覆盖同一批次的两独立 JVM；不同批次交叉共享主数据的并发压力尚未实测。内容/规则冲突拒绝，不能覆写事实；未提交中断回到已审核状态，已提交重试返回原身份。FAILED 必须重新审核，CONFLICT 不自动重试。

正式 V41 `legacy_history_write_guards` 已执行，新增 21 个触发器：历史报工/执行、工单/工艺编辑删除、正式质量/投产/交接/接收/完工/分配/库存动作及领料引用写保护。只有当前原子事务内有对应映射且批次 RUNNING 的历史导入能建立 Execution/Report；不提供会话开关。历史工艺不能被新正常工单引用。

V41 首次因本轮之前的连接 37921 未结束事务而等待 MDL；先终止本轮 DDL 查询，确认未建触发器，再以受限 Flyway repair 清除仅本轮失败的 V41，核对已成功迁移校验和不变。经用户明确授权终止连接 37921 后，正式迁移成功，Flyway validate 41 项通过。仅本轮 DDL 连接设置 5 秒 metadata lock 等待，没有调整全局或持久化参数。V1–V40 未重写。

## 5. 数量规则及真实 S2

旧源码在申报5704/5705时扣对应实际发生工序的本地主材料额度，责任工序不等于发生工序。已转报废/未转报废的0/1状态不抵销既有本地扣减；不能用 ERP 单据成功推断本地损耗。5700、未知/VOID状态、不同物料/单位、非1比例和缺失关联均拒绝统一套公式。

允许规则要求同卡同 route 同实际节点、主投入物料与单位一致、qtyPer=1、无修改事件缺口，且 `净报工 + 已证实损耗 + 当前剩余额度 = 上游有效量`。多条报工和多条损耗只在节点合计一次；晚申报仍归实际发生节点，不移动到责任工序。首序也必须从投入守恒，负余额和无法解释的首序损耗拒绝。未记录的多次修改历史不猜测。

S2 真实样板：8 张流程卡、每张投入400，18工序，145条报工（包含同序多次报工），17条工废/料废原证据，累计损耗49，整单计划3200，末序有效量合计3151。示例卡首序400，第二序旧净报工396、已关联工废4，后序396：

`总加工量 = 原净报工396 + 节点聚合修正4 = 400`

`有效量 = 总加工量400 − 历史有效不良4 + 恢复0 = 396`

员工原始报工保持396，没有虚构额外员工报工4；历史接口同时展示原值、修正和损耗证据。实际 HTTP 逐卡逐节点核对有效量与来源净量一致，当前可报量均0。合成测试另覆盖混合多条损耗、晚不良/不同责任节点、0/1状态、VOID/单位/5700/部件拒绝、修改报工、首序及负余额；这些测试不冒充全部真实分支已验收。
